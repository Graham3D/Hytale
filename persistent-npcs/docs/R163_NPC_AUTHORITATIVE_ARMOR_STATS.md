# R163 NPC Authoritative Armor Stats

Date: 2026-09-05

Revision: `R163-NPC-AUTHORITATIVE-ARMOR-STATS`

Scope: NPC equipment-to-`EntityStatMap` propagation only. Appearance, gear UI, inventory authority, profile persistence, voice, and cognition were not redesigned.

## Result

R163 closes the lifecycle gap that allowed persisted NPC armor to contribute typed damage resistance while its `ItemArmor.getStatModifiers()` entries were absent from the NPC's live `EntityStatMap`. NPC armor, hotbar, and utility containers remain authoritative. Their live state is now reconciled through Hytale's native equipment-stat manager after spawn/hydration and whenever a relevant container changes.

The Profile remains a read-only consumer: Health, Stamina, and Mana are read from the live `EntityStatMap`; Defense continues to use Hytale's typed armor-resistance aggregation.

## Installed Hytale path discovered

Inspection of the installed 0.6.3 server found the native player path in `InventorySystems.LegacyArmorChangeStatSystem`. An armor change schedules `EntityStatMap.getStatModifiersManager().scheduleRecalculate()`.

The public recalculation entry point is:

```java
StatModifiersManager.recalculateEntityStatModifiers(ref, entityStatMap, componentAccessor)
```

Its native armor aggregation:

- reads every equipped `ItemArmor.getStatModifiers()` entry by stat index;
- combines `StaticModifier` values according to their native `CalculationType`;
- writes them to the stat's `MAX` target;
- uses the native stable calculation keys generated by `CalculationType.createKey("Armor")`;
- also reconciles native effect, held-weapon, utility, and broken-item contributions.

R163 calls this installed native implementation rather than copying its arithmetic. The missing behavior was lifecycle scheduling: Orbis can replace or hydrate persisted NPC equipment components without traversing the player armor-change system that normally schedules this recalculation.

Related native metadata audit:

- `ItemArmor.getBaseDamageResistance()` and `getDamageResistanceValues()` remain consumed by `DamageSystems.ArmorDamageReduction`; R163 does not replace that working path.
- `ItemArmor.getRegeneratingValues()` is not consumed by the native equipment modifier manager in this installed build; regeneration remains part of Hytale's separate stat/regeneration machinery.
- `ItemMovementSettings` is presentation/movement configuration and is not mapped into `EntityStatMap` by the native equipment modifier manager.

## Authority and lifecycle

`NpcInventoryRepository` owns the persisted and live NPC equipment containers. It now invokes the equipment-stat bridge at these boundaries:

- `NPC_SPAWN`, after authoritative NPC equipment components are installed;
- `PERSISTED_INVENTORY_HYDRATION`, after persisted state is reconciled into an existing entity;
- `ARMOR_CONTAINER_CHANGE` for equip, replacement, and removal;
- `HOTBAR_CONTAINER_CHANGE` and `UTILITY_CONTAINER_CHANGE`, because the reused native manager also owns held-item and utility stat sources.

`NpcStatRuntimeBridge` performs an additional idempotent native reconciliation at `FRESH_SPAWN_HYDRATION` or `WORLD_RESTORE_HYDRATION` before restoring the persisted current values. This ordering ensures persisted current Health/Stamina/Mana is clamped against the effective bounds that include restored equipment.

Opening or refreshing the NPC Profile does not apply equipment stats. The NPC owns the resulting stats while the UI is closed, and Hytale combat and the Profile consume the same entity component.

## Modifier identity and accumulation safety

The authoritative modifiers retain Hytale's native replacement keys, including `CalculationType.createKey("Armor")`. Native recalculation rebuilds the aggregate from current containers, so repeated spawn/reopen/synchronization replaces the same native keys and cannot stack duplicates.

For bounded diagnostics only, R163 derives a deterministic per-source identity:

```text
NPC_EQUIPMENT:<SLOT>:stat_<INDEX>:modifier_<POSITION>
```

These descriptors identify additions/removals in logs; they do not become a second stat authority and do not duplicate native modifier calculation.

## Native current/maximum semantics

The installed `EntityStatValue` behavior was exercised directly:

- `100/100` plus `+20 MAX Health` becomes `100/120` (equip does not heal);
- applying the same native modifier key again remains `100/120` (replacement, not accumulation);
- if current Health is `120/120`, removing the item clamps it to `100/100`.

R163 preserves these semantics by delegating modifier application and removal to the native manager and hydrating only the persisted current value afterward.

## Development markers

The bounded markers are:

- `NPC_EQUIPMENT_STATS_SYNC_BEGIN`
- `NPC_EQUIPMENT_STAT_APPLIED`
- `NPC_EQUIPMENT_STAT_REMOVED`
- `NPC_EQUIPMENT_STATS_SYNC_COMPLETE`

Per-source markers include stable NPC ID, armor slot, item ID, stat index, native modifier key, deterministic source identity, before current/max, after current/max, and trigger. They do not log unrelated inventory contents.

## Connected validation required

Restart the world/local server, then use an NPC with baseline `100/100` Health:

1. Open `/npc update <name>` and record baseline Health and Defense.
2. Equip `Armor_Copper_Chest` (or another installed armor item with `StatModifiers.Health`). Confirm Health becomes `100/109` and Defense still updates from its typed resistances.
3. Equip a second stat-bearing armor item. Confirm its native modifier contributes once.
4. Close and reopen the Profile. Confirm values do not increase again.
5. Replace the chest item. Confirm the old contribution is removed and the replacement contribution appears once.
6. Unequip it. Confirm the contribution disappears and an over-maximum current value clamps according to native behavior.
7. Close the Profile and exercise damage/healing. Reopen it and confirm the cards show the same live values used by combat.
8. Despawn/reload the NPC, then restart the world/server. Confirm equipment, current values, effective maxima, and Defense return without opening the Profile first.
9. Inspect the four R163 marker families for the NPC stable ID and verify no unrelated inventory contents are present.
