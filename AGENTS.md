# Development baseline and revision safety

- Read `docs/DEVELOPMENT_BASELINE.md` before starting engineering work. Verify its source commit against the actual branch, `git worktree list`, `git status`, build metadata, and any newer committed or uncommitted work. A revision label or an old chat's worktree path alone does not establish the latest source.
- Start new work from the latest verified committed development baseline. Inspect and preserve modified, staged, and untracked files in every relevant worktree before creating another worktree or applying changes. Never reset, clean, restore, overwrite, or remove unrelated work as a shortcut.
- Keep this `AGENTS.md` in every new development worktree. Preserve the separate HyARPG/Hywind and ImmersiveNPCs runtime boundary; the internal plugin identity, entrypoint, and save compatibility require a deliberate review before any migration.
- After each completed engineering pass, record the exact source branch and commit, build revision and version, verification performed, and deployment or connected-QA status in the baseline record. Update `gradle.properties` and generated build identity inputs consistently when a new revision is actually completed. Do not label an uncommitted candidate, a build, or a copied JAR as a new completed or accepted revision.
- Review the complete staged inventory, including newly added files, before committing. Exclude generated binaries, caches, archived saves, player or NPC data, large QA archives, secrets, and unrelated work unless each is specifically reviewed and authorized. Do not force push or destructively clean up a checkout.

# Git task lifecycle, worktrees, and integration policy

These rules are standing authorization to manage the ordinary Git lifecycle of reviewed Hywind task branches. They do not authorize destructive operations, acceptance of untested gameplay, or an unsafe merge. Codex owns tracking and proposing the right next Git action; the user should not need to remember a branch name or request routine post-acceptance integration.

## Start-of-task discovery and source selection

- Before making edits in **every new Codex thread**, inspect `git status --short --branch`, `git worktree list`, relevant local/remote refs, branch upstream and ahead/behind state, `docs/DEVELOPMENT_BASELINE.md`, and any related unfinished task. Fetch remote information when available. Do not assume the current directory, local `main`, highest R-number, latest deployed JAR, or most recent chat is authoritative.
- Identify and report the **latest QA-accepted integrated baseline**, **newest committed development candidate**, **active deployed candidate**, and **relevant unfinished feature branches** when they differ. Build revision, Git commit, branch, QA acceptance, deployment, and integration are separate facts.
- For an independent task, branch from the latest QA-accepted `main` baseline after verification. If the new task genuinely needs code on a newer unmerged branch, explicitly create a **dependent/stacked branch** from that verified commit and record its parent and dependency. Never silently import unrelated, unaccepted gameplay work just because it has the highest revision.
- A new conversation or Codex session does **not** by itself mean a new branch. If it continues the same unfinished feature or its QA fixes, resume the existing task branch after verifying its identity, state, and ownership. Do not start two agents writing to the same branch/worktree concurrently.
- Keep different active tasks in separate worktrees. Before creating or switching worktrees, identify any uncommitted/staged/untracked changes, especially artwork and icons in the primary checkout. Do not stash, reset, clean, move, commit, or overwrite another person's changes without appropriate authorization.

## Determine task boundaries and completion

- Use **feature and acceptance boundaries, not commit counts**, to decide when to branch or merge. A bug fix, polish pass, or required implementation step for an unfinished feature normally stays on that feature's branch.
- Create a separately named task branch when the new work has an independently useful deliverable, independent acceptance criteria, and can reasonably be tested, merged, or reverted separately. Example: Cyclone Armor effects and projectile correction stay with Cyclone Armor; general Combat Damage Trace, trace-command consolidation, and global monster-scaling fixes are separate tasks.
- If unrelated requirements emerge mid-task, finish or safely checkpoint the current work, document the dependency, then start a focused branch from the appropriate verified base. Do not accumulate unrelated foundational features indefinitely on a narrowly named skill branch.
- Track each feature as **IN_PROGRESS**, **ENGINEERING_READY**, **QA_PENDING**, **ACCEPTED**, **INTEGRATION_BLOCKED**, or **MERGED** in the existing development baseline record or linked task/PR. Record task scope, branch, parent commit, dependencies, outstanding acceptance criteria, build/QA evidence, and next action. Deployment is a separate status, never a synonym for acceptance.
- **ENGINEERING_READY** requires the scoped implementation, appropriate regression tests, offline build/asset checks, and reviewed changes, with any known limitations disclosed. A successful commit or JAR package alone is not feature completion.
- For features requiring connected Hytale testing, **QA_PENDING** persists until the user affirmatively accepts the relevant gameplay/UI behavior. User-reported failures keep the same feature open for corrections. Do not infer acceptance from silence, deployment, a log, or a passing offline test.
- For purely internal work without meaningful in-game verification, use its approved measurable engineering acceptance criteria and request owner confirmation if acceptance is ambiguous. Never silently self-approve a gameplay change.

## Automatic promotion to main after acceptance

- The user's affirmative acceptance of a feature's QA is **standing authorization for Codex to perform its routine, non-destructive integration into `main`** once all gates below pass. Do not require the user to remember to request a second merge. If acceptance covers only part of a task or the branch contains unaccepted changes, stop and separate the scope before promotion.
- Before integration, fetch and verify the current remote `main`; confirm the branch's exact commit and ancestry, clean reviewed change inventory, completed acceptance criteria, passed applicable tests, resolved dependencies, and absence of unrelated or uncommitted work in the merge scope. Recheck remote state immediately before publication to avoid racing another thread.
- Never merge a dependent branch while doing so would bring an unaccepted ancestor feature into `main`. First obtain acceptance and integrate the dependency, or safely extract only independent reviewed commits onto an accepted base and retest. Report any changed scope.
- Merge accepted branches into `main` in a **serialized** integration operation. Prefer a reviewable PR or otherwise an auditable non-force integration. If a conflict, unexpected diff, force requirement, ambiguous dependency, failing check, or protected dirty checkout is encountered, mark **INTEGRATION_BLOCKED**, preserve everything, and ask for the minimum necessary decision rather than improvising a destructive workaround.
- Protect the primary checkout and its artwork. Do not discard its changes or switch/reset it to force an integration. If the primary checkout cannot safely be synchronized because of uncommitted work, report that explicitly and propose a safe preservation/integration sequence. Updating GitHub `main` does not prove the primary Windows checkout, source tree, or deployed JAR was updated.
- After integration, verify that the accepted commits are reachable from the actual remote `main`, that the intended files and tests are present, and that no unaccepted features were included. Update the baseline record with exact branch/merge commits, QA evidence, source revision, remote status, and any still-unsynchronized local checkout.
- Never force-push, rewrite shared history, bypass branch protections, create a silent mass merge, or automatically merge experimental work merely because it is older than the latest development revision.

## Mandatory Guardian Git integration audit

- **Required audit events.** Run a read-only Git integration inventory at the start of every new Codex task, at every engineering-stage completion or handoff, when the owner accepts connected QA, and immediately before and after publishing or merging branches. Use the existing Guardian entry points under `tools/guardian/` when implemented; do not claim this new gate already exists simply because `AGENTS.md` requires it. An unavailable Guardian implementation is a tracked enforcement gap, not a successful audit.
- **Enumerate work without changing it.** Compare the fetched remote `main` with the current task branch, its upstream, related local and remote feature branches, all relevant worktrees, and the development baseline/task records. Record each branch's exact HEAD/upstream, ahead/behind and merge-base, unpushed commits, staged/unstaged/untracked files, acceptance state, and stacked dependencies. Do not operate on another task's worktree or treat the highest revision label as authoritative.
- **Classify every relevant feature explicitly.** A completed task must end in exactly one auditable disposition: **INTEGRATED**, meaning accepted changes are verified in remote `main` with intended files/tests present and no unaccepted scope, or **QUARANTINED**, meaning unaccepted, dependent, or integration-blocked work is preserved on a named, tracked branch with its exact commits, reason, responsible next action, and acceptance/integration blocker. Existing `IN_PROGRESS`, `ENGINEERING_READY`, and `QA_PENDING` states remain intact as development/QA states; they are not synonyms for INTEGRATED. Never silently abandon an accepted-but-unmerged branch or describe QA_PENDING as merged/accepted.
- **Audit equivalence carefully.** Test actual reachability from remote `main` for a normal merge; if work was intentionally cherry-picked, rebased, or squashed, independently verify patch/content equivalence, required tests, and traceable original-to-integrated commit mapping rather than falsely claiming the original SHA is reachable. Detect missing accepted changes, duplicate integration, unexpected unrelated changes, incompatible ancestry, and branch publication failures. Do not assume clean textual diffs imply compatible gameplay.
- **Enforce the acceptance-to-integration transition.** An owner-accepted feature that is not verified in remote `main` must trigger the existing safe promotion procedure, or be recorded **INTEGRATION_BLOCKED** with an explicit reason and next action. The routine merge authority in this file does not override a task-specific no-merge restriction, branch protections, unaccepted dependency, dirty worktree, failed verification, or separate deployment authorization. Reviewed QA_PENDING branches may be published on their own tracked branches, but may not be silently promoted to `main`.
- **Fail visibly, not destructively.** If remote refs cannot be fetched, the inventory is incomplete, evidence disagrees, or Guardian cannot execute the gate, report **UNVERIFIED** with the specific missing evidence. Block any claim that integration or release is complete; do not fabricate a pass, force a push, reset a checkout, delete branches, or interrupt legitimate isolated engineering work solely to get a green status.
- **Machine-readable evidence and tests.** Guardian's verification/publication/completion checks must eventually enforce this audit and emit a durable report keyed by source SHA, remote-main SHA, task/branch, status, dependencies, unmatched accepted commits/content, acceptance evidence, and next action. Add isolated Guardian fixtures for: accepted unmerged work, QA_PENDING work, stacked unaccepted parents, a clean accepted merge, an equivalent cherry-pick, unpushed commits, stale remote refs, and protected dirty worktrees. Keep the checks bounded, read-only during inventory, and separate from game deployment. Update `docs/GUARDIAN.md` and Guardian's own tests in the same **separately authorized** enforcement change; adding this policy text alone does not implement the code gate.

## Parallel Codex tasks, revisions, and deployment

- Multiple Codex threads may work concurrently **on different feature branches/worktrees**. Before editing shared files, check whether another active task owns them; coordinate the boundary or stage work sequentially when needed. Git worktrees isolate checkouts, not source-code dependencies or shared deployment state.
- When one task merges into `main`, other active tasks must reconcile the new accepted baseline **before their own integration**, resolve any overlaps intentionally, and rerun affected tests. Avoid unnecessary rebases of published/shared branches; choose safe merge/rebase/cherry-pick based on ownership and review risk. Do not assume absence of textual conflicts means behavior is compatible.
- Prevent competing tasks from claiming the same official cumulative R-revision. Coordinate revision assignment when a cumulative build is finalized; use clearly labeled provisional candidates during parallel development. Never reduce or overwrite a newer accepted revision while packaging an older branch.
- Treat the active RPG save and deployed `Hywind.jar` as **single-writer resources**. Parallel tasks may build offline, but only one authorized deployment operation may replace the JAR at a time. Compare the candidate's full cumulative ancestry with the installed build, ensure the game/server is stopped, back up and hash-verify, and never replace a newer accepted/cumulative build with a stale branch artifact.
- Follow the existing User QA and deployment rules above; a merge is not a deployment, and neither a merge nor deployment is proof of connected gameplay acceptance. Never launch a standalone Hytale server to determine acceptance.
- Retire a feature worktree or remote branch only after confirming its accepted commits are present in `main`, no remaining branch-specific dependencies or valuable local changes exist, and no other Codex task is using it. Worktree cleanup is never an excuse to delete untracked content.

## Required task handoff and completion report

- At the beginning of a task, state the selected branch/worktree, exact base commit, whether `main` is behind the development candidate, and whether the task depends on unmerged work. Keep this concise unless the Git state is unsafe.
- At each engineering completion or task handoff, report: **scope and state** (engineering-ready, QA-pending, accepted, blocked or merged); **local branch/HEAD**; **upstream remote HEAD and ahead/behind**; **working-tree changes**; **dependency branches**; **tests**; **build revision and deployment**; **connected QA**; and **next integration action**.
- Push reviewed feature commits to the matching tracked `codex/` remote branch under the existing Guardian and publication checks. Report push failures and unpushed work explicitly. Do not report `main` as current merely because a feature branch was published.
- Proactively initiate the integration checks when user acceptance is recorded, including in a later thread. When acceptance is missing or blockers remain, retain the branch with a clear next action rather than silently abandoning it.

# Bug investigation and regression prevention

When implementing a fix for a reported Hywind gameplay bug, follow this procedure by default. The user should not need to request these steps individually.

1. **Investigate before modifying.** Inspect the relevant production code, existing Hywind Trace captures, Hytale server logs, related tests, and recent changes. Confirm the actual source revision and distinguish observed evidence from hypotheses. Limit inspection to relevant files and diagnostic windows.
2. **Identify the root cause.** Trace the affected execution path and its interactions with other systems. Do not apply speculative fixes that conceal symptoms. If evidence is insufficient, identify the minimal targeted diagnostic evidence needed.
3. **Reproduce the failure.** Whenever practical, add or extend a targeted JUnit regression test that demonstrates the reported failure before fixing it. For lifecycle, persistence, concurrency, or transactional bugs, use stateful integration tests and fault injection as appropriate. Document when offline reproduction is impractical.
4. **Fix without regressions.** Make the smallest architecturally correct change while preserving gameplay, commands, save compatibility, and subsystem boundaries. Never remove or disable unrelated functionality merely to satisfy tests.
5. **Verify the correction.** Run the relevant JUnit tests and applicable offline build and asset checks. Once configured, use JaCoCo for targeted coverage analysis and SpotBugs for static analysis where useful. Neither coverage numbers nor a clean static analysis report proves the bug is fixed. Avoid blanket full-suite or full-analysis runs for minor changes unless risk justifies them.
6. **Preserve the established QA workflow.** The user reports bugs to ChatGPT and tests fixes in-game. Codex investigates the relevant evidence, implements and verifies fixes, and deploys only when authorized. Never launch standalone Hytale servers for QA. Use Guardian's repository and completion checks where available. Preserve the active RPG save and back up the previous JAR before an authorized deployment.
7. **Report concise, verifiable results.** State the root cause (or remaining uncertainty), correction, tests and results, branch and commit, GitHub synchronization status, deployment status, and short in-game verification steps. Distinguish verified offline behavior from gameplay acceptance.

Prefer targeted evidence gathering and verification to costly repository-wide scans or redundant diagnostics. Do not add new debugging duties to the user's in-game QA workflow.

Use risk-based verification: run focused checks while developing, and batch documentation, version metadata, and reviewed changes before the final required verification where practical. Avoid rerunning the full test suite for documentation-only edits unless Guardian, exact-commit verification, or publication policy explicitly requires it. Never skip a mandatory gate; state when a repeated run is gate-driven rather than code-driven.
