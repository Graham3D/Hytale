# Master Affix base skill scope audit

Audited the working tree against `HEAD` under `docs/MASTER_AFFIX_SCOPE_CORRECTION.md`. This is a source diff audit, not connected gameplay proof. I did not change another worker's runtime files or run Gradle/game/server/auth/deploy commands.

## Actionable scope findings

1. **Quick Slash multi-component proc mechanics changed without an affix.** In `HytaleSkillExecutionSystem.java:2105-2110`, `procAvailable` turns false after the first component with positive premitigation damage. `HEAD` passed `!context.derivedRelease()` to every component; the new code passes `false` to later components even with `GearEffectSnapshot.EMPTY`. `canProc` flows into the native damage metadata and the skill's proc path. Keep the affix receipt capped in its own observer, but retain the HEAD base-skill `canProc` input for each authored component unless a separate base-skill change is authorized. This can suppress later component hit effects; the exact resulting damage depends on the compiled hit procs and is not inferred here.

2. **Existing movement/projectile knockback and passive positioning acquired new targets and force.** `HytaleSkillExecutionSystem.java:2778-2788` replaced an NPC-only `AreaDisplacementPlanner` call with `NativeAffixHostileDisplacement.apply`. `HEAD` returned zero if the target had no `NPCEntity`/`BoundingBox` and used zero scale when the NPC role's knockback scale was nonpositive. The new helper (`NativeAffixHostileDisplacement.java:30-56`) also moves players and does not check that role knockback scale. `HytaleSkillExecutionSystem.java:1983-1990` similarly sends the existing positional passive through that helper; its HEAD path required an NPC and a positive role knockback scale. These are base targeting/control changes with empty target gear. Put the old eligibility/scale in the existing skill callers; allow the shared helper to serve genuine affix displacement separately.

3. **Existing area pulls can stop at a different radius with no affix.** `HytaleSkillExecutionSystem.java:1962-1969` now passes `payload.pullCoreRadius()` to `NativeAffixHostileDisplacement.apply`. That helper caps the requested pull to `distance-to-center - pullCore` before calling the planner (`NativeAffixHostileDisplacement.java:40`). HEAD passed the full authored `payload.pull()` to `AreaDisplacementPlanner`, which capped only at the distance to center. Where the authored pull core is positive, the base skill's movement distance changes. Restore the prior pull geometry for base skill execution; apply WA-082 as a target-side reduction only when present.

4. **Base mastery rank is now frozen through windup.** `SkillExecutionService.java:429-435` removed HEAD's release-time `baseSkillRank` and item-rank recomputation and reuses `prepared.effectiveSkillLevel` from validation. This is appropriate for a committed gear bonus, but if the learned skill's mastery/base rank changes during windup, HEAD released at the new rank and this tree releases at the old one. Keep the item contribution/source frozen while preserving the previous base-rank resolution, or document a separately authorized base-skill transaction change.

5. **Unaffixed Iron Sentinel hit identity/proc metadata changed.** `HytaleSkillExecutionSystem.java:361-405` replaces the single `DamageCalculationService` + `applyObserved` Physical hit with `GearCombatEffects.attack` + `applyGearResolved`. The HEAD native metadata identified the player owner, retained the summon cast root, and set `canProc=false`; the new metadata identifies the Sentinel entity, creates an `/attack/` child root, and sets `canProc=true`, even if its bound item has no affixes. The empty-affix direct Physical amount appears algebraically equal (`base * lease.coefficient()` with zero crit chance), so this audit does **not** claim a proven numeric base-damage change. The identity, proc eligibility, and native handoff are proven mechanics changes; preserve the HEAD metadata/observer contract for an unaffixed Sentinel, or scope the new metadata to a qualifying affix hit.

6. **Summon Health projection now uses a different baseline.** `HytaleSummonSystem.java:422,547` subtracts `NativeNormalHealthMaximum.value(nativeHealth)` when setting `RPG_SUMMON_MAX`; HEAD subtracted `nativeHealth.getMax()`. The new helper excludes timed EntityEffect maximum modifiers. With such a modifier already on the native actor, the final maximum differs from HEAD and the subsequent exact maximum check can reject the summon. This applies to ordinary summons and Sentinel restore without checking for an affix. Retain the HEAD maximum projection for base summons; confine normal maximum calculations to the affix recovery/barrier contexts that require it.

## Changed owners with no established base value violation

- **Cost/cooldown/duration fixtures:** `skills.json`, `stage-09-support-cohort-a.json`, and the baseline count tests have no content diff against `HEAD` (`git diff --numstat HEAD --` returned nothing). The canonical Simulacrum profile remains 20 Mana, 18-second cooldown, and 8-second decoy life in `stage-10-summons-cohort-e.json`. No changed canonical cost, cooldown, duration, target, damage coefficient, or new Ameliorate definition was found. `HytaleSummonSystem.java:433` changes the emitted `lifetime` trace to remaining lease time; it does not set expiry.
- **Resource owner:** `RpgResourceService.evaluateActivation/evaluateUpkeep` add a gear factor whose neutral value is 1; `GearResourceModifiers.activation` starts from the canonical profile cost. The added regeneration overload has zero increase by default. These are generic affix hooks, including the ordinary finite discount for Simulacrum. They do not establish a changed unaffixed base payment.
- **Loadout/acquisition owner:** `OwnershipEntitlementPolicy` and `RpgLoadoutService` add temporary WA-144 item entitlement and revoke it on valid equipment withdrawal; no catalog skill is added and learned ownership is not rewritten. This is an affix grant, not a remap of permanent acquisition. `RpgLoadoutService.java:160-165` does broaden `baseSkillRank`'s rank-one response to *every* unlearned production skill, even with no temporary grant; ordinarily entitlement still prevents those skills from executing. Narrow that condition to `temporaryCopies>0` so nonborrowed callers retain HEAD rank semantics. The new entitlement-aware compilation may also drop a stale unlearned saved loadout; that is an acquisition gate consequence, not evidence of a newly obtainable base skill.
- **Support owners:** `SupportMagnitude`, `FiniteSupportEffects`, `SupportRuntime`, `HytaleSupportSystem`, and `SupportCleanse` add gear percent/magnitude, item aura, and post-removal cleanse receipt hooks. WA-112 consumes a successful cleanse receipt and does not itself remove a status. The new `CLEANSE_BARRIER` kind has no canonical skill profile. These are allowed affix hooks. `FiniteSupportEffects.Effect`'s compatibility constructor sets `baseShieldCapacity=0`; ensure every shield that can reach `reprojectShieldCapacity` is populated by the refresh path first, or an unaffixed shield could collapse to zero on a later projection tick. This is a hook integration risk, not a proven changed authored shield magnitude from the diff alone.
- **Projectile/connection/status hooks:** source snapshots, WA-015/016 projectile travel, WA-082 control reduction, WA-109 channel state, and WA-148..150 item auras are conditional hooks. A null projectile travel quote returns the existing plan. The separate base knockback/pull changes above arise from routing existing skills through a broader helper, not from the presence of those affixes.
- **Documentation and fixtures:** `docs/COMMANDS.md` adds gear QA and diagnostics commands and does not change skill acquisition. The tracked `affixes-v1.json` is unchanged from HEAD but still contains stale "Ameliorate integration needed" and "Simulacrum full-pool drain" contracts at lines 3181-3195 and 3405-3419; the untracked `docs/Master_Affix_v1.0.md` repeats them. Align those texts to the correction. `art/Skills/SkillAmeliorate.png` is an untracked orphan asset; it is not a runtime skill, but remove it if the project is purging the prohibited design.
